Main Building Blocks

The editor is organized into a small set of top-level panels. Each panel focuses on a different part of the configuration.

  1. Configuration Selection: open files, create a new configuration, save, choose configuration type, and select version.
  2. Status Bar: shows save, load, render, and other UI messages with local timestamps.
  3. Additional Metadata: manages safe _metadata. entries separately from normal environment variables.
  4. Service Section: manages top-level service settings such as flush intervals, logging, and other runtime options.
  5. Parsers: defines reusable Fluent Bit parsers that input plugins can reference.
  6. Add Plugin: selects a section and plugin type before adding it to the active pipeline.
  7. Plugins: the main editable pipeline list for inputs, filters, and outputs.
  8. Labels and Workers: Fluentd-only panels for top-level routing containers.
  9. Validation: shows errors and warnings found in the current configuration.
  10. Rendered Configuration: shows the generated Fluent Bit YAML or Fluentd configuration text.

Plugin Sub-Blocks

Plugin cards can contain nested blocks depending on the selected plugin type and configuration engine.

  1. Required and Optional Fields: required fields are always present, while optional fields can be added from the attribute picker.
  2. Processors: Fluent Bit inputs and outputs can contain nested processors grouped by signal such as logs, metrics, and traces.
  3. Route: Fluent Bit 4.2+ input plugins can define conditional routing rules. These nested route blocks let you set per-record routing, signal-specific routes, route conditions, and output targets.
  4. Comments: object-level and field-level comments are stored as editor metadata and can be toggled open when needed.

Routes

The Route panel is used for Fluent Bit conditional routing on supported input plugins.

  1. per_record_routing: enables evaluation of route conditions on each record.
  2. Signal groups: route entries can be organized under groups such as logs, metrics, traces, and any.
  3. Condition: each route can define a default condition or a set of rules with logical operators.
  4. To Outputs: each route points to one or more configured outputs by name or alias.

The editor stores this block internally as route, while rendered Fluent Bit YAML uses the native routes block.

Processors

The Processors block adds transformation logic inside Fluent Bit input and output plugins.

  1. Choose a signal type such as logs, metrics, or traces.
  2. Select a processor definition.
  3. Configure required and optional processor fields.
  4. When supported, add a nested conditional processing block.

Icon Buttons

The UI uses several icon-style controls to reduce clutter. These are the ones to know about.

  1. ?: opens documentation or help for the related item.
  2. 🗒: opens a comment editor when there is no comment yet.
  3. 📝: opens a comment editor when a comment already exists.
  4. ↑: moves a plugin up in its current section ordering.
  5. ↓: moves a plugin down in its current section ordering.
  6. -: removes the related plugin, field, parser, route, or destination entry.
  7. I, F, O: show input, filter, and output placement on plugin cards. The active one is highlighted.

Color Use

Color is used intentionally to separate state and nested structure.

  1. Blue / accent highlights: active controls and current section indicators.
  2. Pale blue route panels: conditional routing blocks and nested route content.
  3. Pale framed comment groups: a field and its comment editor are grouped together visually.
  4. Grey readonly styling: locked metadata such as parser format.
  5. Red labels: required fields.
  6. Green validation header: the configuration validated successfully with no issues.
  7. Amber validation header: warnings are present, but validation is not blocked.
  8. Red validation header: blocking validation errors are present.
  9. Yellow render state: the rendered output is stale because the configuration changed after the last render.

Collapse and Expansion

Most large panels can be collapsed to make the page easier to scan.

  1. Top-level panels such as Parsers, Plugins, Labels, Workers, Validation, and Rendered Configuration can be opened and collapsed.
  2. Plugin cards, parser cards, and route cards can also be collapsed individually.
  3. This helps when large configurations contain many repeated blocks.

Notes on Comments

Comments are editor metadata, not runtime configuration fields.

  1. Object comments and field comments are stored as editor metadata.
  2. Those comments can be rendered into Fluent Bit YAML when comment rendering is enabled.
  3. They are not meant to appear as normal service or plugin attributes.

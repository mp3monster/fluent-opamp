OpAMP Explained: The Control Plane For Observability Agents

OpenTelemetry is often associated with traces, metrics, logs, and the collectors that receive, process, and forward that telemetry. That solves the data movement problem, but it does not fully solve the operational problem of managing hundreds or thousands of agents across clusters, virtual machines, physical servers, remote sites, and edge devices.

OpAMP, the Open Agent Management Protocol, addresses that management layer. It gives a central service and a fleet of collection agents a standard way to exchange identity, health, status, configuration state, and operational instructions.

OTLP carries observability data. OpAMP manages the agents and collectors that handle that data. Put another way, OTLP belongs to the data plane, while OpAMP belongs to the control plane.

What OpAMP Does

OpAMP is a vendor-neutral protocol defined by the OpenTelemetry project. It describes a conversation between an OpAMP Server, which provides central management, and an OpAMP Client, which represents a data-collection agent to that server. The agent can be an OpenTelemetry Collector, Fluent Bit, Fluentd, Elastic Agent, or another telemetry collection process.

Clients send AgentToServer messages containing information such as identity, version, supported capabilities, health, current status, and configuration state. Servers reply with ServerToAgent messages that can offer configuration, commands, connection settings, package information, or other instructions.

These messages are encoded with Protobuf and can be exchanged over HTTP or WebSocket. WebSocket is useful when the server needs to reach an agent quickly, while HTTP works well for a client-driven request and response pattern.

  • Agent discovery and identity reporting.
  • Version, operating-system, and descriptive metadata reporting.
  • Health, status, and heartbeat messages.
  • Remote configuration and reporting whether that configuration was accepted.
  • Restart commands and other operational instructions.
  • Connection detail, credential, package, and software update management.
  • Extensions for agent-specific capabilities.

Implementations do not need to support every possible feature. Clients and servers advertise their capabilities, which lets a server avoid asking an agent to perform an operation it does not understand. That capability exchange is central to using OpAMP across mixed products and implementation maturity levels.

Native Agent Support Is Optional

An OpAMP client can be built into an agent, supplied as a plugin or sidecar, or run as a separate supervisor process. The supervisor pattern is useful for existing agents because the supervisor can speak OpAMP to the central server while translating instructions into local operations for the managed process.

The protocol defines the client and server communication, but it deliberately does not define exactly how a supervisor must start, stop, configure, or inspect a local process. Those details remain specific to the agent and operating system.

How Fluent OpAMP Applies These Ideas

The mp3monster/fluent-opamp project turns this control-plane pattern into a working implementation for Fluent Bit and Fluentd. It includes both sides of the OpAMP conversation plus supporting services for operating and experimenting with the model.

In this project, the provider maps to the OpAMP Server and the consumer maps to the OpAMP Client plus local agent adapter. A minimal deployment needs one provider and at least one consumer, and those pieces can run independently across many machines and environments.

Consumer Lifecycle Modes

Mode What It Does When It Helps
Supervisor Launches the agent and directly manages its lifecycle. New deployments where the OpAMP consumer can own the agent process.
Observer Finds and attaches to an already running process. Existing deployments where OpAMP should be introduced without changing how the process is initially started.

Observer mode is less invasive, but it does not remove the need for operating-system integration. If OpAMP requests a restart, the consumer still needs to know how that service should actually be restarted on the host.

Covered Agents And Current Scope

Fluent Bit and Fluentd have implemented consumer adapters. The repository also includes a simulator for development, demonstrations, and repeatable tests. The architecture leaves room for additional agent types: Elastic Agent is on the roadmap, and the OpenTelemetry Collector is a natural extension target.

Strong areas today include agent identification, capability exchange, health and heartbeat handling, disconnect handling, server error responses, restart commands, and custom messages. Remote configuration is still evolving, while package management and some advanced connection-management features are longer-term work or outside the current plan.

More Than Provider And Consumer

The repository has grown into a small control-plane platform. The provider and consumers remain the core OpAMP loop, while the extra components add operational and collaboration features around that protocol.

  • The Config Service provides editing and validation, primarily for Fluent Bit YAML with some Fluentd support.
  • The Catalog Service discovers known configuration files, displays metadata, and opens files in an editor or read-only viewer.
  • The CLI supports local start, stop, status, and demonstration workflows.
  • The consumer simulator launches multiple scripted consumers for tests and demos.
  • The MCP surface exposes selected provider operations to MCP-capable clients.
  • The agent broker adds a collaboration layer using Slack, LangGraph, and MCP.

These components show the boundary between protocol and product. OpAMP defines the machine-to-machine management conversation; interfaces, catalogues, policy, approvals, and natural-language workflows sit above it. Natural language should still respect normal operational safeguards such as identity, authorization, scope controls, approvals, and audit trails.

A Typical Interaction

  1. A consumer starts and represents a Fluent Bit or Fluentd process.
  2. It connects to the provider and sends identity, description, and supported capabilities.
  3. It continues reporting heartbeats, health information, and meaningful status changes.
  4. An operator selects the agent through the web console, API, CLI, or optional ChatOps route.
  5. The provider checks capabilities and sends a suitable ServerToAgent instruction.
  6. The consumer translates that instruction into a local agent operation.
  7. If the operation changes state, the consumer reports the new state to the provider.
  8. The managed agent continues sending collected telemetry to its normal gateway or observability backend.

That last point is important: OpAMP controls the collection agent, but it does not replace OTLP and it is not the observability data pipeline.

Why It Matters

fluent-opamp makes OpAMP tangible beyond a conversation focused only on the OpenTelemetry Collector. It demonstrates an OpAMP control plane, provides a bridge for bringing Fluent Bit and Fluentd deployments into that model, explores supervisor and observer patterns, and acts as a test bed for capabilities, commands, configuration, fleet simulation, MCP, and ChatOps.

It also surfaces the questions any production control plane must answer: how configuration is versioned and rolled back, how credentials are delivered, how identity is established, who can issue commands, what happens when only part of a fleet accepts a change, and how results are audited. OpAMP does not answer every governance question by itself, but it provides a common protocol on which consistent answers can be built.
